# Research: self-dismissing Chimes

Question: how can a delivered Chime remove itself from the Android tray / iOS Notification Center shortly after sounding (about 1 minute), without the app being opened?

Date: 2026-11-05. Pinned versions: expo 57.0.27, expo-notifications 57.0.22, React Native 0.86, androidx.core 1.17.0 (from `node_modules/expo-notifications/android/build.gradle:36`), minSdk 24 / targetSdk 36 (`node_modules/react-native/gradle/libs.versions.toml:3-5`).

Abbreviations used in citations: `EN-A` = `node_modules/expo-notifications/android/src/main/java/expo/modules/notifications`, `EN-I` = `node_modules/expo-notifications/ios/ExpoNotifications/Notifications`, `EN-S` = `node_modules/expo-notifications/src`.

Blocked by the sandbox firewall (HTTP 403, "Approval required"): `developer.android.com`, `developer.apple.com`, `docs.expo.dev` (direct fetch; the Expo MCP docs tools worked), `pnpm.io`, `cs.android.com`, `android.googlesource.com`, `notifee.app`. Fallbacks used: AOSP framework source from the GitHub mirror `aosp-mirror/platform_frameworks_base` (archived, last push 2025-11-12, so framework citations reflect that snapshot), the androidx.core 1.17.0 sources jar from `dl.google.com`, Apple SDK headers (iOS 27.2 SDK) from the GitHub mirror `xybp888/iOS-SDKs`, pnpm docs from `github.com/pnpm/pnpm.io`. Apple's prose documentation pages could not be read; where a claim rests on them it is marked.

## Summary / recommendation options

Baseline already in place, worth knowing before choosing: on Android, expo-notifications posts every delivery with tag = request identifier and id = 0 (`EN-A/service/delegates/ExpoPresentationDelegate.kt:37,108-112,127-129`), and Android replaces a posted notification with the same tag and id (AOSP `core/java/android/app/NotificationManager.java:710-711`). Since each Chime Slot uses the fixed identifier `chime-<slot>` (`src/notifications/chimes.ts:46-47`), the tray already holds at most one Chime per Chime Slot (up to ~60), not one per day. The app also clears all delivered notifications whenever it comes to the foreground (`src/hooks/use-chime-scheduling.ts:10-13,22-30`).

## 1. Android: patching expo-notifications

### Where the notification is built

- Call chain for a scheduled Chime: the AlarmManager alarm fires the `PendingIntent` from `NotificationsService.createNotificationTrigger` (`EN-A/service/NotificationsService.kt:416-440`) → `ExpoSchedulingDelegate.triggerNotification` re-reads the stored request, calls `NotificationsService.receive(...)` and immediately re-schedules the next day (`EN-A/service/delegates/ExpoSchedulingDelegate.kt:72-77`) → `ExpoHandlingDelegate.handleNotification`, which in the background calls `NotificationsService.present(context, notification)` when title or text is non-empty (`EN-A/service/delegates/ExpoHandlingDelegate.kt:118-148`, present at 137); in the foreground it asks the JS handler first (same file 124-131) → `ExpoPresentationDelegate.presentNotification` (`EN-A/service/delegates/ExpoPresentationDelegate.kt:94-114`) → `createNotification` (`:159-162`) → `ExpoNotificationBuilder.build()`.
- Builder classes: `interface NotificationBuilder` with `setAllowedBehavior` and `suspend fun build(): android.app.Notification` (`EN-A/notifications/interfaces/NotificationBuilder.kt:10-26`); `abstract class BaseNotificationBuilder` creating the `NotificationCompat.Builder` with the trigger's channel (`EN-A/notifications/presentation/builders/BaseNotificationBuilder.kt:23-37`, channel lookup 39-79); `open class ExpoNotificationBuilder` (`EN-A/notifications/presentation/builders/ExpoNotificationBuilder.kt:33`). There is no `CategoryAwareNotificationBuilder` in 57.0.22 (not present in the source tree).
- The `NotificationCompat.Builder` is configured in `ExpoNotificationBuilder.build()` at `ExpoNotificationBuilder.kt:92-157`: `createBuilder()` at 93, small icon/priority 95-96, `setAutoCancel(content.isAutoDismiss)` and `setOngoing(content.isSticky)` at 100-101, title/text/subtext/style 104-109, sounds 115, `content.body` (JSON) into extras 117-122, marshalled request into extras 128-138, content intent 140-148, `builder.build()` at 156. This is where a patch would add `setTimeoutAfter`.
- Posting: `NotificationManagerCompat.from(context).notify(notification.notificationRequest.identifier, getNotifyId(...), androidNotification)` (`ExpoPresentationDelegate.kt:108-112`), with `getNotifyId` returning `ANDROID_NOTIFICATION_ID = 0` (`:37,127-129`).

### Fields that could carry a timeout

- Existing timeout support: none. `grep -i timeout` over the package's `android/src`, `ios` and `src` finds only the 3-second JS handler timeout in `EN-A/notifications/handling/SingleNotificationHandlerTask.java:26-32`.
- `autoDismiss` is not a timer: it maps to `setAutoCancel` (dismiss on tap) — `ExpoNotificationBuilder.kt:100`; the TS docs say "Corresponds directly to Android's `setAutoCancel` behavior" (`EN-S/Notifications.types.ts:598-607`).
- Arbitrary data does reach the builder: `NotificationContentInput.data?: Record<string, unknown>` (`EN-S/Notifications.types.ts:560-563`) is read from the `data` key into `NotificationContent.body` (`EN-A/notifications/ArgumentsNotificationContentBuilder.java:23,43,95`), exposed as `INotificationContent.body: JSONObject?` (`EN-A/notifications/interfaces/INotificationContent.kt:29`), and survives scheduling because it is parcelled/serialized with the request (`EN-A/notifications/model/NotificationContent.java:170,194,221,251`). So a custom builder or delegate can read e.g. `content.body?.optLong("timeoutAfterMs")`.

### Is the builder pluggable?

- There is no factory or meta-data key for the builder. Meta-data read by the builder is only icon, large icon and color (`ExpoNotificationBuilder.kt:400-405`).
- The supported extension point is a `BroadcastReceiver` subclassing `NotificationsService` that supplies its own `PresentationDelegate`. The CHANGELOG for 0.8.0 states the override mechanism changed "from defining an `expo.modules.notifications#NotificationsScoper` meta-data value in `AndroidManifest.xml` to implementing a `BroadcastReceiver` subclassing `NotificationsService` delegating those responsibilities to your custom `PresentationDelegate` instance" (`node_modules/expo-notifications/CHANGELOG.md:1104`).
- The hooks exist: `open class NotificationsService` (`EN-A/service/NotificationsService.kt:30`), `protected open fun getPresentationDelegate(context)` (`:615-616`), `open class ExpoPresentationDelegate` (`ExpoPresentationDelegate.kt:31`), `protected open suspend fun createNotification(...)` (`:159-162`). `ExpoNotificationBuilder` is `open`, but `createBuilder()` is a final member of the base class (`BaseNotificationBuilder.kt:34`), so overriding the builder means re-implementing `build()`; overriding the delegate's `createNotification` is simpler.
- How the subclass gets picked: every internal command (`present`, `receive`, alarm triggers) is sent to the first receiver found for action `expo.modules.notifications.NOTIFICATION_EVENT` in the app package (`NotificationsService.kt:386-393,403-406`). The library's own receiver is declared with `android:priority="-1"` (`node_modules/expo-notifications/android/src/main/AndroidManifest.xml:15-18`), and `PackageManager.queryBroadcastReceivers` returns matches "ordered from best to worst" (AOSP `core/java/android/content/pm/PackageManager.java:7969`). A subclass receiver with the default priority 0 should therefore win. Unverified on a device: confirm with a log line in the subclass.
- Stability across versions: on expo `main` (expo-notifications 58.1.6) `NotificationsService` is still `open`, `getPresentationDelegate` still `protected open` (line 646), `createNotification` still `protected open suspend` (line 281), and the receiver still uses priority -1. Fetched from `raw.githubusercontent.com/expo/expo/main/packages/expo-notifications/...` on 2026-11-05.

### Sketch of the subclass (approach 1)

- Kotlin in a local module: `class ChimeNotificationsService : NotificationsService() { override fun getPresentationDelegate(context: Context): PresentationDelegate = ChimePresentationDelegate(context) }` and `class ChimePresentationDelegate(context: Context) : ExpoPresentationDelegate(context) { override suspend fun createNotification(notification, behavior): android.app.Notification { val built = super.createNotification(notification, behavior); val ms = notification.notificationRequest.content.body?.optLong("timeoutAfterMs") ?: 0; return if (ms > 0) NotificationCompat.Builder(context, built).setTimeoutAfter(ms).build() else built } }`. All names except `ChimeNotificationsService` / `ChimePresentationDelegate` / `timeoutAfterMs` are confirmed in the sources cited above; `context` is a `protected val` of `ExpoPresentationDelegate` (`ExpoPresentationDelegate.kt:32`).
- `NotificationCompat.Builder(Context, Notification)` exists in androidx.core 1.17.0 ("Creates a NotificationCompat.Builder which can be used to build a notification that is equivalent to the given one", `androidx/core/app/NotificationCompat.java:1160-1161` in `core-1.17.0-sources.jar`) and copies extras (`addExtras(getExtrasWithoutDuplicateData(...))`, same constructor), so the marshalled request that `getPresentedNotificationsAsync` relies on (`ExpoPresentationDelegate.kt:164-174`) is kept. Not verified by a build: whether every field survives the copy; a fallback is the framework `Notification.Builder.recoverBuilder(Context, Notification)` (AOSP `Notification.java:7318-7324`).
- `NotificationCompat.Builder.setTimeoutAfter(long)`: "Specifies the time at which this notification should be canceled, if it is not already canceled. No-op on versions prior to O" (`NotificationCompat.java:2432-2443` in 1.17.0). Framework javadoc: "Specifies a duration in milliseconds after which this notification should be canceled, if it is not already canceled" (AOSP `Notification.java:4730-4740`). Android 8.0 (API 26) and later only; the app's minSdk is 24, so Android 7.x devices keep the current behaviour.
- The OS enforces it: `NotificationManagerService.scheduleTimeoutLocked` sets `AlarmManager.setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP, now + timeoutAfter, pi)` (AOSP `services/core/java/com/android/server/notification/NotificationManagerService.java:9885-9891`) and cancels with `REASON_TIMEOUT` (same file, e.g. 1892). It runs in system_server, so it works while the app process is dead and in Doze.
- Gradle: the module needs expo-notifications on its compile classpath, e.g. `implementation project(':expo-notifications')`. Precedent for referencing another autolinked Expo module by project name: `node_modules/expo-dev-client/android/build.gradle:40-43`. Unverified for this project until the first build.
- Manifest (module's `android/src/main/AndroidManifest.xml`, merged by Gradle like any library manifest): a `<receiver android:name=".ChimeNotificationsService" android:exported="false">` with an intent filter for `expo.modules.notifications.NOTIFICATION_EVENT` only. Boot actions don't need to be repeated: the library's own receiver still receives `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` (`AndroidManifest.xml:21-26`) and re-arms alarms, and the re-armed `PendingIntent`s target the subclass because `createNotificationTrigger` resolves the designated receiver (`NotificationsService.kt:425-427`).
- Migration gotcha (dev devices only, app unreleased): the trigger `PendingIntent`'s request code is the receiver class name's hash (`NotificationsService.kt:436`), so alarms armed before the subclass existed are not matched by later `cancelAll` calls. Each such alarm fires once more, then stops re-arming against the old component. Reinstalling the dev build avoids this.
- Scope: the foreground path also goes through `createNotification` when the handler shows the notification in the list (`shouldPresentAlert` = banner || list || alert, `EN-A/notifications/model/NotificationBehaviorRecord.kt:25-27`; the app sets `shouldShowList: true`, `src/notifications/chimes.ts:74-80`), so foreground Chimes time out too.

### (a) `pnpm patch` (approach 2)

- Flow: `pnpm patch expo-notifications@57.0.22`, edit `android/src/main/java/expo/modules/notifications/notifications/presentation/builders/ExpoNotificationBuilder.kt` (e.g. after line 101: read `content.body?.optLong("timeoutAfterMs")` and call `builder.setTimeoutAfter(it)` when > 0), then `pnpm patch-commit <dir>`. That writes the patch file to `patches/` and registers it under `patchedDependencies` in `pnpm-workspace.yaml` (pnpm docs `docs/cli/patch.md`, `docs/cli/patch-commit.md` in `github.com/pnpm/pnpm.io`).
- Maintenance: keys can be exact versions or ranges; "A patch that fails to apply fails the install", and unused patches fail the install unless `allowUnusedPatches: true` (same `patch.md`). Every expo-notifications bump means re-checking or re-creating the patch. The builder file already changed between 57.0.22 and `main` (Android `group` support added right after `setOngoing`), so the patch would need rework at the SDK 58 upgrade.
- Repo constraints: patching changes `pnpm-lock.yaml`, and this repo's rules say dependency installs happen on the host, not in the sandbox (`CLAUDE.md`, Agent Instructions). It needs a native rebuild like any Kotlin change. Benefit over approach 1: none functionally; it only saves the Gradle/manifest wiring.

### (b) Config plugin (approach 3)

- `android/` is git-ignored (`.gitignore:42`, CNG), so native edits must come from prebuild. A config plugin works on the generated native project, not on `node_modules`. Its realistic form is approach 1 in another shape: a dangerous mod writes the subclass Kotlin into `android/app/src/main/java/...`, and an `AndroidManifest` mod adds the receiver (or uses `tools:node="remove"` on the library receiver). A local Expo module gets both for free (autolinking plus manifest merge), and the repo already has one (`modules/exact-alarm`). Not recommended.

## 2. Android: a local Expo module without touching expo-notifications

- Approach 1 above is already a local module, and it doesn't modify expo-notifications; it only subclasses its public extension point.
- Approach 4, the own scheduler: the module would post Chimes itself (`NotificationCompat.Builder(...).setTimeoutAfter(...)`) from its own `BroadcastReceiver`, armed by `AlarmManager.setExactAndAllowWhileIdle` (same calls expo uses, `EN-A/service/delegates/ExpoSchedulingDelegate.kt:105-121`). Required pieces:
    - persist the slot list and channel, re-arm the next day on every fire;
    - handle `BOOT_COMPLETED`, because alarms "will be cleared if it is turned off and rebooted" (AOSP `apex/jobscheduler/framework/java/android/app/AlarmManager.java:58-63`);
    - handle `MY_PACKAGE_REPLACED`, as expo does (`NotificationsService.kt:33-39`);
    - handle `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`, which is sent when the permission is granted, "will not be sent when the user revokes the permission" (`AlarmManager.java:165-181`);
    - keep the existing JS flows (cancel-all on Pause, clear-on-open, foreground handling).

  That duplicates most of what expo-notifications does for Chimes and splits Android and iOS onto different code paths. Only worth it if more Android-only behaviour is wanted later, e.g. `setAlarmClock`.
- Approach 5, the cancel alarm: a module alarm at slot time + 60 s calls `NotificationManagerCompat.cancel("chime-<slot>", 0)`. The tag and id are known: tag = request identifier, id = 0 (`ExpoPresentationDelegate.kt:108-112,37`); expo itself cancels by `(identifier, getNotifyId(...))` (`:143-155`) and cancels everything with `cancelAll()` (`:157`). Downsides: a second exact-alarm chain to keep in sync with expo's schedule, plus its own BOOT_COMPLETED re-arm. Strictly worse than approach 1.
- NotificationListenerService: it must be protected by `BIND_NOTIFICATION_LISTENER_SERVICE` (AOSP `core/java/android/service/notification/NotificationListenerService.java`, class javadoc), and the user has to enable notification access in system settings (Android docs blocked; this is the well-known special-access flow, unverified here). It only adds visibility into other apps' notifications. The app can already cancel its own. Rejected.
- How expo-notifications handles reboot: the library manifest adds `RECEIVE_BOOT_COMPLETED` (`node_modules/expo-notifications/android/src/main/AndroidManifest.xml:2`). The `NotificationsService` receiver listens to `BOOT_COMPLETED`, `REBOOT`, `QUICKBOOT_POWERON` (two variants) and `MY_PACKAGE_REPLACED` (`:15-28`). `handleIntent` routes these to `onSetupScheduledNotifications` (`NotificationsService.kt:643-645,828-829`), which re-schedules every request stored in SharedPreferences (`ExpoSchedulingDelegate.kt:22-31`). The Expo v57 docs confirm the boot permission is "used to set up scheduled notifications when the device (re)starts" (`https://docs.expo.dev/versions/v57.0.0/sdk/notifications/`, Permissions → Android, read via Expo MCP).
- Reboot and the tray: delivered notifications aren't restored after a reboot, so a self-dismiss mechanism has nothing to clean up after boot. This is standard platform behaviour, not verified against a source in this session.

## 3. Alternative library

- `@notifee/react-native`: the GitHub repo `invertase/notifee` is archived (GitHub API `archived: true`, last push 2026-04-07). The latest release is `@notifee/react-native@9.1.8` from 2024-12-20 (GitHub releases API; npm `dist-tags.latest` 9.1.8). The README opens with "Notifee is no longer actively maintained… We recommend that users migrate to expo-notifications… Alternatively, see the community-maintained fork react-native-notify-kit" (`raw.githubusercontent.com/invertase/notifee/main/README.md`). The maintainer's explanation is in issue #1254, comment 3456588135 by mikehardy (2025-10-28): "Expo 'won'". Notifee did support `android.timeoutAfter` (`packages/react-native/src/types/NotificationAndroid.ts:378` on its `main`), but an archived library is not an option for an SDK 57 / RN 0.86 app.
- `react-native-notify-kit` (`github.com/marcocrupi/react-native-notify-kit`): not archived, last push 2026-11-05, latest release v10.10.0 (2026-10-28), npm latest 10.10.0, about 219 stars, 2 open issues, one named maintainer (README: "continued and improved by Marco Crupi"). The README says "New Architecture only (TurboModules)", "Expo CNG / prebuild support for development builds. Expo Go is not supported", "Development target: React Native 0.85.3". Peer dependencies are `react-native >=0.73.0` and `expo *` (npm metadata, and `packages/react-native/package.json`). Compatibility with RN 0.86 / Expo SDK 57 is unverified, since the dev target is 0.85.3.
    - `timeoutAfter`: `NotificationAndroid.timeoutAfter?: number`, documented as "Sets the time in milliseconds at which the notification should be automatically cancelled once displayed" (`packages/react-native/src/types/NotificationAndroid.ts:407-411`). It is applied via `builder.setTimeoutAfter(...)` (`packages/react-native/android/src/main/java/app/notifee/core/NotificationManager.java:319-320`).
    - Triggers: `TimestampTrigger` with `repeatFrequency` (`RepeatFrequency.DAILY = 1`) and `repeatInterval`, plus `alarmManager?: boolean | TimestampTriggerAlarmManager`. AlarmManager is the default ("By default, timestamp trigger notifications use AlarmManager on Android"), and `AlarmType` covers `SET`, `SET_AND_ALLOW_WHILE_IDLE`, `SET_EXACT`, `SET_EXACT_AND_ALLOW_WHILE_IDLE` and `SET_ALARM_CLOCK` (`packages/react-native/src/types/Trigger.ts`, `TimestampTrigger`/`AlarmType`/`RepeatFrequency`). The implementation uses `AlarmManagerCompat.setExactAndAllowWhileIdle` / `setAlarmClock`, with a fallback when `canScheduleExactAlarms()` is false (`.../app/notifee/core/NotifeeAlarmManager.java:260-336`). The next DAILY timestamp is computed with `Calendar.add(DAY_OF_MONTH, …)`, i.e. in local time (`.../core/model/TimestampTriggerModel.java:143-166`).
    - Reboot: `RebootBroadcastReceiver` for `BOOT_COMPLETED` and the two QUICKBOOT actions, calling `rescheduleNotifications` (`.../core/RebootBroadcastReceiver.java:28-60`, manifest `packages/react-native/android/src/main/AndroidManifest.xml`). `MY_PACKAGE_REPLACED` isn't registered, and behaviour after an app update is unverified. An `AlarmPermissionBroadcastReceiver` handles `SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` (same manifest).
    - Custom sounds per channel: `createChannel(channel: AndroidChannel)` exists (`packages/react-native/src/NotifeeApiModule.ts:297`). The exact `AndroidChannel.sound` semantics (raw resource name) and how the Expo plugin bundles sound files were not verified; the notify-kit config plugin's documented options cover the NSE and notification icons, not sounds (README "Expo CNG" sections). Other APIs present: `openAlarmPermissionSettings` (`NotifeeApiModule.ts:426`), `createTriggerNotification` (`:434`), `cancelDisplayedNotification(id, tag?)` (`:253`), `getNotificationSettings` (`:698`).
- Other candidates: none found that are maintained and offer Android `timeoutAfter` with exact daily triggers. The search wasn't exhaustive beyond the forks the Notifee README names. expo/expo has no issue or PR mentioning `timeoutAfter` / `setTimeoutAfter` (GitHub issue search, 0 results).
- Cost of switching: rewrite `src/notifications/chimes.ts` (channels, per-slot DAILY timestamp triggers, cancel-all, clear-on-open, foreground handler), `src/notifications/permissions.ts` and the activation flow. Sound bundling would need re-solving, since today the expo-notifications config plugin copies `assets/sounds/*.wav` (`app.json` plugins). Then either drop expo-notifications on both platforms or run two notification stacks, with a risk of conflicting notification-center delegates on iOS (unverified). Plus a new native dependency on a single-maintainer fork. iOS gets nothing for this. The cost is far higher than approach 1 for the same Android result.

## 4. iOS

- Notification Service Extension: the SDK header describes the override as "You are expected to override this method to implement push notification modification" (`UserNotifications.framework/Headers/UNNotificationServiceExtension.h:18-20`, iOS 27.2 SDK). Apple's documentation page (blocked; content seen only via search-engine summaries of `developer.apple.com/documentation/usernotifications/unnotificationserviceextension` and "Modifying content in newly delivered notifications") says it customizes the content of a remote notification, and runs only for remote notifications with an alert and `mutable-content: 1`. Conclusion: it doesn't run for locally scheduled Chimes. That conclusion rests partly on unread Apple prose.
- Notification Content Extension: `didReceiveNotification:` is called to show a custom interface when the notification UI is displayed (`UserNotificationsUI.framework/Headers/UNNotificationContentExtension.h:120-130`), i.e. when the user expands the notification, not at delivery. It can't drive a timed removal.
- No expiry API: `UNMutableNotificationContent` exposes `threadIdentifier`, `targetContentIdentifier`, `interruptionLevel`, `relevanceScore`, `filterCriteria` and others, and no expiration or timeout property (`UNNotificationContent.h:55-148`; a `grep -i expir` over all UserNotifications headers only hits the service extension's `serviceExtensionTimeWillExpire`).
- `removeDeliveredNotificationsWithIdentifiers:` / `removeAllDeliveredNotifications` are plain instance methods of `UNUserNotificationCenter` (`UNUserNotificationCenter.h:73-75`). They act only when called, so some app or extension code has to be running; there is no scheduled variant. expo-notifications wraps them as `dismissNotificationAsync` / `dismissAllNotificationsAsync` (`EN-I/Presenting/PresentationModule.swift:17-23,32-38`). The app already calls `dismissAllNotificationsAsync()` on every foreground (`src/notifications/chimes.ts:84-86`, `src/hooks/use-chime-scheduling.ts:10-13`). On Android the same call is `NotificationManagerCompat.cancelAll()` (`ExpoPresentationDelegate.kt:157`).
- JS can't wake on delivery: Expo v57 docs for `registerTaskAsync` say "When the app is terminated, only a Headless Background Notification triggers the task execution" (headless = remote data-only push), so a local Chime can't run cleanup code (`https://docs.expo.dev/versions/v57.0.0/sdk/notifications/`, "Run JavaScript in response to incoming notifications", via Expo MCP).
- Background tasks: `BGAppRefreshTaskRequest` asks the system to launch the app briefly, and "The system will fulfill this request intelligently based on system conditions and app usage". `earliestBeginDate` only guarantees the task "won't begin sooner" (`BackgroundTasks.framework/Headers/BGTaskRequest.h:24-42`). `BGProcessingTaskRequest` is fulfilled "within the next two days as long as the user has used your app within the past week" (`:57-61`). `expo-background-task` uses BGTaskScheduler with a processing identifier (`com.expo.modules.backgroundtask.processing`, `processing` background mode). Its docs say tasks run only with sufficient battery and available network, the minimum interval is 15 minutes, and "On iOS, short intervals are often ignored—the system typically runs background tasks during specific windows, such as overnight" (`https://docs.expo.dev/versions/v57.0.0/sdk/background-task/`, via Expo MCP). Usable at most as a coarse, best-effort sweep; it can't remove a Chime about one minute after it sounded.
- `interruptionLevel`: `passive` means "Added to the notification list; does not light up screen or play sound", which kills the Chime sound. `active` means "Presented immediately; Lights up screen and may play a sound". `timeSensitive` may break through Do Not Disturb (`UNNotificationContent.h:20-33`). None removes the notification. expo-notifications 57.0.22 supports setting it: `NotificationContentInput.interruptionLevel` (`EN-S/Notifications.types.ts:629-638`), applied natively at `EN-I/NotificationRecords.swift:384-386`.
- `relevanceScore`: "determines the sorting for the notification across app notifications" (`UNNotificationContent.h:83-84`). It only sorts, doesn't remove, and expo-notifications doesn't expose it (no occurrence in `ios/` or `src/`).
- `threadIdentifier`: "It will be used to visually group notifications together" (`UNNotificationContent.h:59-60`). Grouping reduces visual clutter but not the count. In expo-notifications 57.0.22 it is read-only: it appears in the delivered-notification record (`EN-I/NotificationRecords.swift:297,322`; output type `NotificationContentIos.threadIdentifier`, `EN-S/Notifications.types.ts:482-483`), but `NotificationContentInput` has no such field and `toUNMutableNotificationContent()` never sets it (`EN-I/NotificationRecords.swift:336-389`). With no thread identifier, iOS groups an app's notifications into one stack by default. That default is from Apple's docs and not verified here, but it matches issue 05's "all Chimes grouped into one stack" without any code.
- Sound without a Notification Center entry: presentation options (`.sound`, `.list`, `.banner`, `.badge`) apply only in `willPresentNotification`, which "will be called on the delegate only if the application is in the foreground" (`UNUserNotificationCenter.h:81-97`). In the background the user's settings decide. The app can read but not change them: `notificationCenterSetting`, `lockScreenSetting`, `alertStyle` and `soundSetting` are `readonly` (`UNNotificationSettings.h:62-84`). The user can switch off Notification Center for the app in iOS Settings; whether sounds still play with every alert style off is unverified and needs a device test. Whether a local notification with a sound but no title/body plays its sound without being listed is also unverified.
- Same-identifier replacement on iOS: whether a repeating calendar trigger's next delivery replaces the previous delivered notification with the same request identifier (as Android's tag replacement does) is unverified.
- Silent remote pushes to wake the app and clear: they would need a server, contradicting ADR 0001's OS-scheduled, offline design. Apple also recommends not sending "more than two or three per hour", as quoted in the Expo v57 notifications docs. Rejected.
